## 2. Can a whole model work in the background, like the Reader? (measured)

Why the Reader works off screen: it is a 14 M-parameter model on the **CPU**. The MLX and Core AI models are already inside the app; what stops them is iOS, not where the model lives: an app that isn't on screen may not use the **GPU** unless it is signed with Background GPU Access (his sideloaded builds aren't, X38-05), and iOS ends a background app that keeps the CPU busy for about a minute (Pass 27: MLX on the CPU, killed after ~90 s).

Measured on this M1 Pro (Qwen3.5 4B, 4-bit):

| Engine | prefill tok/s | answer tok/s |
|---|---|---|
| MLX, GPU | 158 (1,024 tokens) | 33 |
| MLX, CPU | < 1 (512 tokens didn't finish in 10 min) | — |
| llama.cpp (b12110), CPU, 2 threads | 39 | 12.9 |
| llama.cpp, CPU, 4 threads | 76 | 21.2 |
| llama.cpp, GPU | 372 | 38 |

So the CPU can run a 4B model — with llama.cpp's CPU code, not MLX's. iOS's two rules then decide when: **off screen while you listen**, paced to under half of one core averaged over a minute (iOS's limit); **overnight in the processing task that waits for a charger**, where iOS lifts the CPU limit (WWDC19 707: "turn that off for the duration of your processing task … while the device is plugged in") — full speed. Weights are memory-mapped from the file, so iOS can page them instead of counting 2.4 GB as the app's memory.

**The engine has to be built from source.** llama.cpp's own Apple release (b12110 xcframework) is compiled for the oldest ARM: its iOS slice contains **0** dot-product (`sdot`) instructions and its macOS slice 153; in the Mac lab it read Qwen3.5 4B at **1.3 tok/s** prefill / 1.0 answer where Homebrew's llama.cpp read 20.5 / 5.5 at the same settings, back to back. Built from the same source with the CPU features on (`Scripts/build-llama.sh`: iOS ARMv8.4 + dot product + int8 matmul — the int8 kernels are picked at run time only on chips that have them; Mac native; Metal off; Accelerate on): 1,117 `sdot` and 284 `smmla` in the iOS library, and the lab read **17.7 tok/s / 6.0** vs Homebrew's 18.3 / 4.0 under the same load. The official release would have run ~13× slower on the phone.

**Built** (device builds only — no simulator slice, like Core AI): `Packages/LlamaCPU` (`llama.xcframework` built by `Scripts/build-llama.sh` from llama.cpp b12110, git-ignored, rebuilt when missing — by `generate-project.sh`, `device-build.sh` and a new step in the IPA workflow; `LlamaEngine`: CPU and Accelerate devices only, memory-mapped weights, greedy, prompt reuse when the model allows), `CPUReading` (the GGUF pinned to unsloth/Qwen3.5-4B-GGUF @ e87f176, Q4_0, 2,583,221,408 bytes, SHA-256 checked; download/delete; on/off), `CPUBudget` (rest after each step: the app's CPU time ÷ 0.45 − the step's wall time), `OvernightWindow` (full speed only inside a processing task requested with a charger, while charging), `CPUJudge` (the app's prompts, windows of 3,000 tokens, answer parsing and saved-answer checkpoint, engine on its own queue). `ProcessingPipeline.readOffScreenOnCPU`: when the app isn't on screen and an MLX or Core AI read would be left for the screen, the CPU copy reads instead; if it isn't downloaded or fails, the old behaviour stands. Settings → MLX models → **Reading in the Background**. Lab: `Tools/CPULab` (the same engine and prompts on the Mac).
