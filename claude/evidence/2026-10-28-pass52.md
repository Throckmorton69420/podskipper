## 3. Ternary Bonsai 2 4B: a Swift loader (source + lab)

- **Found.** PrismML publishes the Hadamard layers in its mlx-swift fork (pinned here) but no Swift loader: the pack's `model_type: prism_hadamard_qwen35` is unregistered, and its readme says loading the tensors as ordinary 2-bit layers produces wrong output without failing. Their own loader is Python (`runtime/vision_artifact.py`); no PrismML `mlx-swift-lm` fork exists (checked their GitHub org).
- **Built.** `Services/LocalModel/PrismBonsai2.swift`: registers the type with `LLMTypeRegistry` (from `LocalJudge`, before the one MLX load); builds the stock Qwen3.5 text model from `text_config` (tied head from the pack's top level); in `sanitize`, swaps each listed module (200 projections + the embedding) for `HadamardQuantizedLinear` / `HadamardQuantizedEmbedding` from the pack's own `.signs` tensors before the weights apply — they are already `Quantized`, so the loader's quantize step skips them, and the strict weight check fails the load if any swap didn't happen. Vision tower and signs dropped. The delta-net's grouped head order (`repeated`) matches the pack's `gdn_activation_layout: grouped`, so nothing is permuted; the fused input projection declines Hadamard layers (exact-type check), so they run as themselves. `LocalModelSpec.bonsai2_4B` (1.88 GB: weights, tokenizer, JSON; the downloader already skips `mtp/` and `runtime/`), experimental.
- **Lab (Mac, `mlx-lab … hello`, the same loader file symlinked):** loads in 2.6 s and answers "4", "Paris", "Yes" (to "is this an ad?" on a Squarespace read) — a wrong transform loads and writes nonsense, so this is the check that matters.
- **Lab (25-episode dev set, `phone_judge.py … p-listener`, same instructions and labels as Pass 44's Qwen3.5 4B):**

| Model | Heard s/h | Show cut s/h | Breaks missed |

  It misses about twice as many breaks. Kept in the list as experimental with that in its description; Qwen3.5 4B stays the default.
